## Why this phase exists

Aeolus already has much of the command architecture we want. `CommandService` is the physical-command boundary, `PendingCommandTracker` handles correlated acknowledgement and observation, the MQTT path can attach MQTT 5 correlation data and response topics, automation executions have execution IDs, and MQTT/device events already flow through the internal event bus.

Phase 1 does **not** replace those systems. It closes the gaps that prevent the next automation/demo architecture from being truthful and observable:

1. Generic MQTT devices cannot currently declare acknowledgement capability, even though the dispatch path can already send a correlation envelope.
2. Command lifecycle progress is mostly transient/log-based rather than a durable, queryable timeline.
3. `PendingCommandTracker` is intentionally in-memory, so a process restart can erase the live wait even though the physical command may already have been dispatched.
4. Event context lacks a common causal/provenance envelope.
5. Scoped automations cannot use raw MQTT publish, which is correct for security, but this also means there is no safe first-class way for automation silos to communicate over MQTT.
6. The backend does not yet expose the command/event data needed for the later automation UI to visibly prove request -> dispatch -> ACK -> observation.

## Locked Phase 1 decisions

These are design decisions, not suggestions for Kiro to silently reinterpret.

- Keep `CommandService` as the **only verified physical-command boundary**.
- Keep raw `mqtt.publish()` as unverified transport. Do not turn it into a verified command shortcut.
- Keep the existing lifecycle states: `REQUESTED`, `DISPATCHED`, `ACKNOWLEDGED`, `OBSERVED`, `FAILED`, `TIMED_OUT`, `STATE_MISMATCH`.
- Add a `commandId` for every verified command. `correlationId` remains a transport/confirmation correlation identifier and is not a replacement for `commandId`.
- Make command history durable, including individual lifecycle transitions.
- Do **not** replay physical commands automatically after a process restart. Unfinished tracked commands are reconciled as interrupted/failed in history. Automatic replay would be unsafe and is out of scope.
- Generic MQTT acknowledgement capability is configured per device and persisted.
- Add a safe automation-event API that publishes through a reserved MQTT namespace generated by Aeolus. Scoped automations may use this API without receiving arbitrary MQTT publish authority.
- Automation-event provenance is observability metadata, not an authorization credential. Never trust a broker payload merely because it claims a source automation ID.
- Automation-event chains have a bounded causal depth so a circular A -> B -> A workflow cannot publish forever.
- Phase 1 adds backend/API/WebSocket support only. No new command timeline UI, flow graph, automation detail redesign, seeded scenario rewrite, or mock actuator implementation belongs here.

## Definition of Phase 1 complete

Phase 1 is complete when a test can demonstrate this full backend-only chain:

```text
registered generic MQTT device
        |
        | configured ACK-capable
        v
CommandService
        |
        | commandId + correlationId
        v
MQTT command publish
        |
        | responseTopic + MQTT 5 correlationData
        v
simulated/test MQTT client
        |
        | ACK { correlationId, success: true }
        v
PendingCommandTracker
        |
        v
ACKNOWLEDGED
        |
        +--> durable command transition history
        +--> command lifecycle WebSocket event
        +--> queryable command API
```

and a second test can demonstrate:

```text
Automation A
  events.emit("tank.low", payload)
        |
        v
reserved Aeolus MQTT event topic
        |
        v
MQTT ingest (not device discovery)
        |
        v
Automation B trigger
        |
        +--> receives causal/provenance metadata
```

Those two chains are the foundation for the mock hardware and automation redesign that follow.
